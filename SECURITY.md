# Безопасность проекта

Сайт — статические файлы на GitHub Pages. Своего сервера нет, поэтому всё, что лежит
в `index.html`, `app.js`, `admin/` и `config.js`, **видно любому посетителю** (Ctrl+U)
и любому, кто открыл репозиторий. Из этого следуют два правила:

1. **Секретных ключей в коде сайта быть не может.** Не «спрятать поглубже», не
   «обфусцировать» — не может в принципе. Все секреты живут в Cloudflare Worker
   (папка `worker/`), браузер обращается к нему и предъявляет токен входа Firebase.
2. **Клиентские проверки — только для удобства.** Настоящие ограничения задаются
   в `firestore.rules` и в воркере. Кнопку в браузере можно нажать в обход интерфейса,
   правило Firestore — нельзя.

## СРОЧНО: отозвать утёкшие ключи

Эти ключи были закоммичены в публичный репозиторий и попали на живой сайт. Они
**скомпрометированы навсегда** — удаление из кода не помогает, старые версии
остаются в истории git и в кэшах поисковиков. Их нужно именно отозвать.

### 1. Токен Telegram-бота

Лежал в `index.html` (`TELEGRAM_BOT_TOKEN`) в десятках коммитов, включая последний.
Кто угодно может писать от имени бота и читать всё, что боту пишут.

- Откройте [@BotFather](https://t.me/BotFather) → `/mybots` → выберите бота →
  **API Token** → **Revoke current token**.
- Новый токен **не вставляйте в код**. Задайте его секретом воркера:
  `wrangler secret put TELEGRAM_BOT_TOKEN`

`TELEGRAM_CHAT_ID` (id чата получателя) секретом не является, но тоже переехал в воркер.

### 2. Ключ ImgBB

Лежал в `admin/index.html` и `admin/admin.js` (`IMGBB_API_KEY`), в 54 коммитах.
Позволяет постороннему заливать любые файлы в аккаунт ImgBB.

- Зайдите на [api.imgbb.com](https://api.imgbb.com/) под своим аккаунтом и
  перевыпустите ключ (Revoke / Regenerate).
- Новый ключ — секретом воркера: `wrangler secret put IMGBB_API_KEY`

### 3. Firebase apiKey — отзывать НЕ нужно

`AIzaSy...` в `config.js` — не пароль, а публичный идентификатор проекта. Он и должен
быть в коде сайта. Защита — в правилах Firestore. Но ограничить его стоит:

- [Google Cloud Console → Credentials](https://console.cloud.google.com/apis/credentials)
  → ключ Browser key → **Application restrictions → HTTP referrers** →
  добавьте `https://voroninkostroma.ru/*` и `https://teassty.github.io/*`.
- Firebase Console → Authentication → Settings → **Authorized domains** — оставьте
  только свои домены.

### 4. История git (по желанию)

Даже после отзыва старые токены остаются в истории репозитория. Отозванный токен
безвреден, поэтому переписывать историю не обязательно. Если всё же хочется вычистить —
это `git filter-repo` + `git push --force`, что переписывает все коммиты; делать это
стоит осознанно и с резервной копией.

## Как поднять воркер

Воркер (`worker/index.js`) — единственное место с секретами. Два маршрута:
`POST /notify` (уведомление о заказе в Telegram) и `POST /upload` (загрузка фото на ImgBB).

```bash
npm install -g wrangler
wrangler login
cd worker
wrangler secret put TELEGRAM_BOT_TOKEN
wrangler secret put TELEGRAM_CHAT_ID
wrangler secret put IMGBB_API_KEY
wrangler deploy
```

После `wrangler deploy` вы получите адрес вида
`https://voronin-relay.ВАШ-АККАУНТ.workers.dev`. Его нужно прописать **в трёх местах**:

1. `config.js` → `export const RELAY_URL = "https://..."`
2. `index.html` → в `connect-src` внутри `Content-Security-Policy`
3. `admin/index.html` → там же в `connect-src`

Без пункта 2 и 3 браузер заблокирует запрос — политика безопасности не пускает на адреса,
которых нет в белом списке.

Проверьте `ALLOWED_ORIGIN` в `worker/wrangler.toml`: там перечисляются домены, с которых
воркер принимает запросы (через запятую). Сейчас это `https://voroninkostroma.ru`,
`https://www.voroninkostroma.ru` и `https://teassty.github.io` (зеркало GitHub Pages).

Пока `RELAY_URL` пустой, сайт работает: заказы сохраняются в Firestore и видны в `/admin/`,
просто без Telegram-уведомления. Загрузка нового фото в панели покажет понятную ошибку.

## Как задать администратора

Права администратора = наличие документа `admins/<uid>` в Firestore. Писать в коллекцию
`admins` запрещено отовсюду, она заполняется только руками через консоль.

1. Firebase Console → Authentication → Users → скопируйте **User UID** нужного аккаунта.
2. Firebase Console → Firestore Database → создайте коллекцию `admins`, в ней документ
   с ID, равным этому UID. Содержимое документа не важно (можно одно поле `role: "admin"`).

**Порядок важен.** Сначала создайте документ, только потом публикуйте правила:

```bash
firebase deploy --only firestore:rules
```

Иначе панель `/admin/` останется без прав на запись и вы не сможете её восстановить
из интерфейса — только через консоль.

> `firestore.rules` в репозитории — источник правды. Правила, набранные руками в консоли
> Firebase, при следующем `firebase deploy` будут заменены содержимым этого файла.

## Проверить, что правила действительно применены

Файл `firestore.rules` мог ни разу не деплоиться — тогда в проекте до сих пор действуют
правила по умолчанию. Тестовый режим Firestore (`allow read, write: if true`) означает,
что **любой человек может стереть весь каталог и прочитать все заказы** — с именами,
телефонами и почтой покупателей.

Проверка: Firebase Console → Firestore Database → вкладка **Rules**. Там должно быть
то же, что в `firestore.rules`. Если видите `if true` или дату истечения тестового
режима — деплойте правила немедленно.

Быстрая проверка снаружи (должно вернуть `403 PERMISSION_DENIED`):

```bash
curl -i "https://firestore.googleapis.com/v1/projects/voronin-jewelry/databases/(default)/documents/orders?pageSize=1"
```

`200` здесь — это утечка персональных данных покупателей.
Для `products` `200` — норма, каталог читается публично по замыслу.

## Что защищает что

| Угроза | Где закрыто |
| --- | --- |
| Посторонний пишет в каталог | `firestore.rules`: `products` — write только `isAdmin()` |
| Покупатель выдаёт себе права админа | `admins` — `allow write: if false`, заполняется вручную |
| Заказ от чужого имени | `orders.create`: `d.uid == request.auth.uid`, `d.email == token.email` |
| Правка отправленного заказа | `orders.update`: админ, и только поле `status` |
| Чтение чужих заказов | `orders.read`: свой `uid` или админ |
| Кража токена бота / ключа ImgBB | Секреты только в воркере, не в коде сайта |
| Спам в Telegram через воркер | `/notify` требует вход + подтверждённую почту + существующий заказ в Firestore |
| Загрузка чужих файлов на ImgBB | `/upload` проверяет `admins/<uid>`, тип и размер файла |
| Запрос с чужого сайта | Воркер: белый список `Origin`, CORS |
| XSS через данные заказа/каталога | `escapeHtml()` перед каждым `innerHTML` + CSP |
| Чужой скрипт на странице | CSP: `script-src 'self' https://www.gstatic.com` |
| Кликджекинг на панели | Выход из фрейма в начале `admin/admin.js` |
| Посторонний видит интерфейс панели | Проверка `admins/<uid>` в `admin/admin.js` |

## Известные остаточные риски

- **`/notify` можно вызвать без реального заказа.** Исправлено: воркер требует `orderId` и
  проверяет, что документ заказа существует в Firestore, принадлежит вызывающему и создан
  не более 10 минут назад. Без реального заказа уведомление в Telegram не уходит.
- **Текст Telegram брался из тела запроса, а не из Firestore.** Исправлено: после проверки
  `orderId` воркер читает документ заказа и собирает сообщение только из полей базы.
- **Состав `items` в заказе проверяется по количеству, но не по содержимому.** Правила
  Firestore не умеют перебирать элементы списка. Ограничение — 100 позиций и лимит
  Firestore в 1 МБ на документ.
- **Каталог `products` читается публично** — это осознанный выбор: так работает и сайт,
  и почасовая синхронизация `catalog.json`. Товары не являются секретом.
- **Нет HTTP-заголовков безопасности** (`X-Frame-Options`, `X-Content-Type-Options`,
  `Strict-Transport-Security`). GitHub Pages их ставить не даёт. Частично заменено
  `<meta>`-политикой; полностью решается переездом на Cloudflare Pages или Netlify.
